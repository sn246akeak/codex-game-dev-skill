# 策划规格与文档分层

用于项目 PRD、模块 micro-PRD 的编写与修订。文档服务于当前版本，不增加项目范围、额外审批或新的状态系统。

## 三类产物

- 项目 PRD：版本目标、目标体验、核心循环、模块边界与依赖、场景概览、版本验收、明确不做事项。
- 模块规格：目的、玩家行为、触发与生命周期、状态和数据、界面反馈、异常边界、配置及资源、具体验收。简单模块保持短小，复杂模块再展开；不机械复制所有检查维度。
- 实施与验证记录：实际改动、验证方法与结果、局限、用户决定及可复用命令。由现有 workflow 关联，不把过程日志塞入正式策划正文。

同一规则指定唯一归属文件及章节，其他文档引用。公司格式是同一规格的交付视图，记录来源和版本；修订先更新归属规格，再同步受影响交付物，避免两份规则独立演化。已验收模块的行为变更沿用修订模块机制，不重写历史。

## 从材料重建规则

先检查实际文件、日期、版本与决策记录。文件中的“建议”可能在后续实施确认中被批准；较新的实现也可能只是默认实现。遇到冲突沿可追溯的确认与版本归属核对，不能单凭文件时间或代码存在推定产品批准。

把截图、想法和会议纪要还原成完整操作：谁在何时进入 → 是否满足条件 → 按什么顺序检查 → 修改什么状态 → 玩家看到什么 → 何时允许下一步。成功、失败、取消、退出和恢复只检查本功能适用部分。可见入口应有去向，去向应有行为说明；不能把截图边界当成全部功能边界。

区分观察事实、已批准规则、常规实现推导和重大未决选择。普通可逆细节在范围内处理并简记依据；涉及核心体验、经济、奖励、硬性限制、时序、存档损失或验收的未决选择集中询问。已有授权直接沿用，不能因换模块、换格式或补充说明再次索取。

随机模块按需说明候选筛选、权重来源、抽取次数、重复/冲突、无候选与零权重处理、结果保存及重开/续玩的区别；不要编造概率或承诺必定可解。时间模块明确时长与时点、边界、重置及中断恢复。经济模块明确产出/消耗、上限、重复发放和失败后结果；统计仅定义有实际决策或诊断用途的事件。这些维度只在当前模块涉及时展开。

## 写作约定

用户已有模板和术语优先。否则以自然中文按操作或对象组织，用一句话解释整体后再展开条件和结果。并列属性同级，条件从属于对应规则；每条表达一个有用结论。避免“按需处理”“由配置决定”却不说明实际含义。

默认 Markdown，允许有助理解的字段表、状态表和验收表。内部推理清单不直接作为正式目录。前期体验推演可以在设计稿中探索；正式规格只纳入确定的结果。讨论稿可以清楚标记问题，正式终稿不得把假设写成已确认规则。

规则触及配置时读取 [data-workflow.md](data-workflow.md)，触及 UI 时读取 [ui-behavior-specs.md](ui-behavior-specs.md)，交付文案/图片时读取 [copy-and-resources.md](copy-and-resources.md)。实现前执行 [document-review.md](document-review.md)。公司交付按 [company-delivery.md](company-delivery.md) 另行排版。
