# 文档审查与开发交接

起草后、进入开发前检查适用项。修订只检查改动及受影响关系；不要求每个微小编辑另走一轮审批。记录具体缺口、位置、影响与处理，不凭字数或标题齐全判定完成。

## 检查内容

1. 目的与范围：规则是否服务版本目标，是否扩大范围；模块划分是否有可验收的玩家结果。
2. 功能闭环：入口、资格、操作、按序校验、状态变化、成功/失败反馈、退出与恢复能否连起来；是否漏了可见入口的去向。
3. 确定性：关键术语、单位、数量边界、结算时点、选择结果、配置来源是否明确；不适用的网络/经济异常不强加。
4. 一致性：图文、配置与规则是否冲突，共享规则是否唯一归属，后续授权是否已合并，代码默认是否被误当产品确认。
5. 可读性与交付：具体自然的项目语言、正确并列层级、适用截图/文案/资源对应；公司版式只在公司模式检查。
6. 可验证性：关键规则有输入、操作和预期结果；验收覆盖正常路径与会改变结果的边界。程序测试、视觉检查和真实试玩分别记录。

将问题区分为阻塞产品决定、开发歧义、调优风险、表达修正。常规可逆事项直接处理；重大未决项集中询问，仅暂停依赖部分。不存在的外部依赖另行记录，不把引用写成已验证。

## 通过的含义

规格就绪表示规则足以实施且批准来源可追溯，不代表程序实现、测试通过或用户验收。存在影响该模块实施的重大未决事项时，交付讨论稿与问题记录，不能标为终稿或 ready_to_build。已有批准与可独立实施的范围保持有效。

工作记录保留来源、决策、缺口与审查结论；正式终稿保留确定规则。实现验证仍按 module-handoff 和 workflow-runtime 执行，不能用文档覆盖检查替代实际测试。
